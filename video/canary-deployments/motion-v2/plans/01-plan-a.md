# Lesson 01 — Keep a control version

## Teaching intention

One mechanism: retain version 1 as the concurrent control, give version 2 a limited share of requests, observe comparable outcomes from both, and let a criterion chosen beforehand determine promote, pause or abort. A changing traffic share or elapsed timer alone cannot supply that decision. Target 46 seconds, finite ending; shorten transitions if needed, never add idle time to reach a duration. No narration or on-screen paragraphs. This is a production plan only, not a rendered or verified video.

## Example and evidence boundaries

Use a fictional read-only API with one request operation, `GET /items`. Both versions receive comparable mixes of request size and client type in the same ten-minute observation window. Use the same failure definition and measurement method for both. Assignment is independent of these request characteristics in the example; do not contrast easy control requests with difficult candidate requests. The illustrated routing share is 90% / 10%, a scenario choice, not a recommendation or a guarantee about real routing. Label it `Example traffic`; show measured counts later rather than suggesting configuration proves exposure.

Before exposing v2, establish this deliberately simplified exercise rule: wait for the complete comparable window and at least 1,000 observed requests per version. Missing observations, an incomplete window, or an unfair comparison means pause. With those prerequisites satisfied, candidate errors more than five percentage points above control mean abort; otherwise the exercise permits promotion. This numerical rule is teaching material, not a production policy, statistical significance test, or claim that passing proves safety. No inferred causal attribution: an observed difference can justify stopping exposure under the rule without proving the deployment caused it.

Final fictional window: v1 has 90 errors / 9,000 requests = 1%; v2 has 90 errors / 1,000 requests = 9%. Equal raw error counts deliberately make denominators matter, without teaching a separate aggregation lesson. The difference is eight percentage points, exceeding the five-point allowance. These are aggregate illustrative measurements, not counts inferred from the few animated request markers. Keep `Illustrative` visible during the rule and results. Do not show tiny animated samples generating statistical confidence.

Version identity never changes to green merely because requests arrive. Requests are small square data markers on routed connectors, not envelopes, vehicles, birds, pipes, or other physical metaphors. Application actors are software service panels, not hardware racks. No decorative dashboard chrome.

## Sound and motion implementation notes

All sounds synthesised; no music, voice, stock effects, or physical-world sound metaphors. Keep v1 at C5, v2 at E5, router at G5, decision/comparison at G4 with G3 for threshold failure. Pitch denotes identity, never relative health. Pan to the current actor coordinates, reducing stereo spread after rows become full width; meaning must survive mono playback. Sends lower gain than arrivals; only meaningful aggregate events sound during dense traffic. Use short sine-based notes with restrained echoes and gentle attacks. Mix below -1 dBFS peak and check that the decision event remains audible without startling volume.

Use scheduled state changes, packets, bars, labels and sound events from the local pinned renderer. Pure time-based animation must scrub deterministically. Custom result-row drawing, if needed later, belongs beside this cut, not in the installed skill. Store counts as explicit fixtures and derive 1%, 9% and the eight-point delta arithmetically. Do not invent a stream of individual outcomes that purports to account for 10,000 requests. No render, code, fixture, or metadata changes are part of this planning task.

## Accuracy and scope checks

- Every observation belongs to a named version, the same operation, the same window, and a comparable request mix. No old v1 baseline versus new v2 window.
- The timer completion permits evaluation; it cannot trigger promotion by itself. Both result rows visibly feed the decision.
- Pause means do not expand while evidence is incomplete or incomparable. Promote is an allowed exercise outcome, not a displayed guarantee. Abort ends candidate exposure in this example; it does not prove root cause or undo prior effects.
- Do not add pooled-error masking, critical-operation segmentation, sequential statistics, replica-weight mechanics, provider configuration, retry policy, rollback compatibility, health-check recovery or an escalating rollout schedule. Those would dilute lesson 01.
- Avoid implying a five-point threshold, ten-minute duration, 1,000 requests, or 10% exposure is generally safe. All are conspicuously illustrative. A real policy needs workload-specific evidence and safety constraints beyond this simplified rule.

## Planned verification and learner check

Inspect the complete 350 px playback without zooming. Count text lines, verify minimum type size, connector separation and digit readability. If a rule row fails, simplify the layout or give it a separate reveal; never shrink its text. Check audio by listening and analysing peaks; record these as separate checks. Decode the entire encode, check duration and streaming metadata, and verify no lingering metric or selection from a previous composition. These checks are planned, not claimed complete.

Observable learner test: after one viewing, identify v1 as control and v2 as candidate; explain why both have observations; select abort from 1% versus 9% under the displayed rule. In a verbal follow-up, remove either denominator: the answer must change to pause. Ask whether waiting ten minutes alone approves v2: the answer must be no. No exercise UI is added to the video.
