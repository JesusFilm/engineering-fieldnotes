## Timestamped first findings

- **A, 1.6–12.2 and 14.5–20.5:** the same API/DB pair runs first serially and then in parallel. Progress bars make overlapping work easy to see; Reconcile remains 1/2 until the second return. This is the cleanest concurrency introduction and the only cut to visibly give reconciliation its own work interval. It does not show failed or stale evidence, or a human decision. Experienced engineers already understand overlap, so it offers less new practice than C.
- **A, 12.2–14.5:** serial success resets into parallel without a new problem or visible input identity. This is an illustrative scheduling comparison, not evidence of speedup or equivalence. Preserve that boundary in its transcript. **20.5–25.97:** success holds and then a long black tail; inspect exact fade timing before deciding whether to shorten.
- **B, 1.5–5.5:** tests and docs land as independent outputs in a shared-code box. **7.5–11.2:** a field changes from amount to total_cents while a concurrent handler still uses amount; the red mismatch and redo packet make the cost of a hidden dependency concrete. This is the most useful complement to C: it teaches when splitting is unsafe, not merely how to wait.
- **B, 9.7–14.5:** green tests:ok persists over changed, visibly inconsistent code and through repair. This is a substantial teaching weakness: stale success appears to certify a different snapshot. Clear or mark those results stale when code changes. **21.5–23.5:** tests and the dependent handler run together, with tests:ok appearing around the handler update. Unless these are explicitly independent test artifacts, this repeats the dependency mistake in the purported solution. Ensure validation follows the final code change.
- **B, 9.7/13.5/19.5/23.5:** the field/handler strings are readable at full size but comparatively demanding at 350px; four narrow rows, changing worker labels, colored bracket and ripples compete for attention. Ripples cross code rows and the Shared code label without fully obscuring them. The final sequenced state has a useful hold around 24–25s, but the exact last frame retains a bright title while the body has faded. Check the intended loop boundary.
- **C, 1.5–8.3:** a frozen patch fans out; the join counts returned passes and only then sends to a distinct approver. Larger labels are easiest to read at 350px. The success-before-failure structure establishes the normal contract without a paragraph of explanation.
- **C, 13.5–17.5:** first report produces 1/2, the red second report changes the join to BLOCKED, and nothing approval-ready goes downstream. Strong causal teaching. However, Approver stays WAIT with no failure notification, which can imply humans never receive blocking evidence. The written guide explicitly requires immediate visibility. Show a failure notice reaching the human while keeping approval blocked.
- **C, 18.5–27:** PATCH C resets both results before rerunning. This is the strongest match to the guide's conservative snapshot invalidation exercise. The engineer's repair itself is implicit, and PATCH A/B/C identity is expressed in labels rather than packet payloads. A roughly one-second approved hold before PATCH B is brisk; the final approved hold is more generous. It must not be presented as a universal requirement to rerun every check or as proof model PASS means correct.

## Preliminary comparative judgement

C is the strongest main chapter entry: fixed-input fan-out, incomplete join, failure blocking, new-snapshot invalidation, and distinct approval form one useful operating rule. B is a valuable dependency-design complement, conditional on fixing stale success and validation ordering. A is a clear scheduling primer and should remain available without being stretched into a second copy of C. No pass quota or author identity influenced this judgement. Final scores and recommendation wait for source/transcript checks, correction, and encoded verification.
