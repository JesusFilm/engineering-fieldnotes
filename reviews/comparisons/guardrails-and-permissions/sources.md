# Guide and technical-boundary verification

Primary documents retrieved and read 2026-10-19. This is a content review, not an audit of a deployed authorization system.

| Primary document | Relevant support and boundary |
| --- | --- |
| [OWASP Authorization Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html) | Least privilege, default denial, authorization on each request, trusted enforcement location, and safe failure support the guide’s restricted investigation identity. A resource and operation matter as well as identity; a valid schema does not establish access rights. |
| [OWASP LLM Prompt Injection Prevention](https://cheatsheetseries.owasp.org/cheatsheets/LLM_Prompt_Injection_Prevention_Cheat_Sheet.html) | Agent-specific defenses and model-based guardrails distinguish fallible screening from tool scopes and execution-side permission checks. Retrieved/tool content can carry indirect instructions. This supports the Fable scenario without claiming every model follows every injection. Scoped reads still carry disclosure risk. |
| [OWASP Transaction Authorization](https://cheatsheetseries.owasp.org/cheatsheets/Transaction_Authorization_Cheat_Sheet.html) | Significant transaction data must be reviewable, protected from change, and checked at execution; changed data invalidates authorization. Applying this to service, environment, and immutable artifact is the library’s engineering design inference, not a claim that OWASP specifies release record r42. Token replay, expiry, and atomic execution controls remain omitted from the animation. |
| [MCP tools, pinned 2025-06-18 specification](https://modelcontextprotocol.io/specification/2025-06-18/server/tools) | Security Considerations separately requires input validation and access controls on servers. Client confirmation for sensitive operations is a recommendation. Tool metadata/labels are not implementation evidence. This source is deliberately versioned; no assertion about a newer version is needed. |
| [GitHub deployments and environments](https://docs.github.com/en/actions/reference/workflows-and-actions/deployments-and-environments) | Environment jobs can be gated by reviewers; approval controls availability of environment secrets. The document also states plan/repository limitations, default administrator bypass, and lack of automatic container isolation on self-hosted runners. The guide correctly requires separate configuration review. A reviewer gate alone does not prove an immutable-artifact binding or close alternate credential paths. |

## Placement and exercise

Keep **core**, following tool-design and before connecting an agent to shared-system credentials. The guide changes an immediate engineering decision: which identity can reach which endpoint, and how to prove denial leaves state unchanged. It defines guardrail and authorization, exposes broad-shell bypasses, separates a trusted reviewer from model-supplied approval, and gives an observable fixture exercise with successful reads, a permitted exact release, denied writes, and denied changed targets. These make it suitable for the team's initial transition rather than occasional reference material.

No substantive guide rewrite was needed. Retrieval dates were added to the five source entries. The video is not a security proof: none depicts credential isolation, authentication, race/replay control, compromised infrastructure, or a failed/unavailable permission service. The guide explicitly requires default denial, but the videos demonstrate denied permissions rather than a service outage. No claim is made that the separate notes’ Simon Willison reference was independently checked in this pass.
