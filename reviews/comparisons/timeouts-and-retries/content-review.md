# Content and primary-source review

Reviewed 2026-10-19. **Keep/core**, after tool design. Before delegating remote work unattended, the team needs a runtime-owned deadline, a bounded retry policy, and an honest unknown result. These change implementable behaviour now; they are not merely distributed-systems trivia. The classification is editorial judgement. Provider-specific details support the decision as reference material.

The guide’s engineering example is coherent: two total attempts, each capped at five seconds, fit a twelve-second operation budget only if the two-second example delay and all overhead fit too. The corrected text says “at most” five remaining seconds. Limits must come from measured latency and task tolerance; none of the video timings is a recommendation.

Primary pages were opened and their relevant text read, not merely search snippets. Links below paraphrase the checked boundaries; retrieval date for all is 2026-10-19.

| Primary document | Checked claim and editorial consequence |
|---|---|
| [AWS Builders’ Library: timeouts, retries, backoff and jitter](https://aws.amazon.com/builders-library/timeouts-retries-and-backoff-with-jitter/) | Retries can amplify load, and layers multiply attempts; choose ownership deliberately. Timeout does not establish that effects did not happen. Timeout coverage may omit DNS/TLS or connection work. Retain latency-based policy selection, include all operation phases, and count downstream arrivals. |
| [gRPC deadlines](https://grpc.io/docs/guides/deadlines/) | Deadline expiry can cancel the RPC, but server application code must stop spawned activity. Propagation deducts elapsed time. Guide now explicitly recommends propagating cancellation and cooperative work while refusing to infer rollback. |
| [gRPC retries](https://grpc.io/docs/guides/retry/) | No configured retry policy does not mean no transport retries. Transparent retries depend on how far a call progressed, including unlimited retries when it never left the client and one when the server library saw it but application logic did not. Keep the one-application-owner rule without claiming exactly one physical transmission. |
| [RFC 9110 §9.2.2](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2.2) | Idempotency concerns intended effect, not identical responses; automatic retries of non-idempotent operations require known safety or non-application. The read examples cannot justify automatically retrying arbitrary writes. |
| [Stripe idempotent requests](https://docs.stripe.com/api/idempotent_requests) | API v1 can replay the first saved status/body, including errors after execution starts. Keys may be pruned after at least 24 hours; parameter consistency and execution-start rules matter. Validation/concurrent-conflict cases are not simply saved results. Keep the explicit v1 scope and avoid a universal permanent-key promise. |
| [AWS: exponential backoff and jitter](https://aws.amazon.com/blogs/architecture/exponential-backoff-and-jitter/) | Unjittered exponential retry waves can remain clustered; randomized timing spreads work across clients in the studied scenario. A single animated sampled delay cannot prove this population effect. All three cuts retain that limitation. |

The operation identity rule is this guide’s design recommendation, not a protocol requirement: repeated requests for the same bounded task share exhaustion; a genuinely new task or separately scheduled poll can receive a new budget. Neither an identical build ID forever nor arbitrary model rephrasing should define that boundary alone. This clarification prevents the recommended gate from accidentally prohibiting all future CI polling.

The exercise now uses four modes and observable logs: real success, delayed completion, retryable persistent failure, and invalid argument. It distinguishes late remote completion from an accepted caller result; confirms non-retryable failure is not retried; checks actual downstream calls and hidden client settings; and tests that repeating an exhausted operation does not reset its allowance. This is a proposed team exercise, not a claim that production infrastructure or a live client integration was tested here.
