# Primary-source and relevance review

Retrieved and read on 2026-10-19. Findings are paraphrases; the exercise and curriculum placement are editorial judgements, not RFC claims.

- [RFC 7636 §§4.1–4.6](https://www.rfc-editor.org/rfc/rfc7636#section-4.1): verified fresh random verifier per attempt, permitted 43–128-character range, recommended 32 random octets, S256 transformation including ASCII and unpadded base64url, challenge/method association with the code, verifier submission at token exchange, and invalid_grant for unequal transformed values. A successful comparison continues normal OAuth processing. The letters and hash labels in these cuts are symbolic; the guide gives the full transform. The RFC's abstract flow supports omitting browser internals for this narrow lesson.
- [RFC 6749 §5.2](https://www.rfc-editor.org/rfc/rfc6749#section-5.2): missing required token-request parameters are categorized as invalid_request. Baseline showed no verifier yet named invalid_grant. Revised outcome is NO TOKEN, preserving the certain protection without turning provider error handling into this cut's lesson.
- [RFC 9700 §2.1.1](https://www.rfc-editor.org/rfc/rfc9700#section-2.1.1): verified public-client PKCE requirement, confidential-client recommendation, application beyond native/mobile clients, and transaction-specific binding to the initiating client/user agent. Added this last boundary explicitly to the guide: indexing records alone does not establish trustworthy callback/session binding. The concurrency bug is an illustrative application of these requirements, not the authorization-server mix-up attack.
- [RFC 8252 §§4, 6](https://www.rfc-editor.org/rfc/rfc8252#section-4): verified native applications' external-user-agent authorization practice and browser recommendation. The guide's desktop-host scenario fits. No claim is made that the model itself should receive the credentials.
- [MCP HTTP authorization, version 2025-11-25](https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization): verified HTTP versus STDIO applicability, PKCE support discovery and refusal when required metadata is absent, S256 when technically capable, and intended-recipient validation. The protected tool service is the resource server in the chapter; the host's client performs OAuth. An MCP server can itself be a client to an upstream API, but that separate architecture is not the diagram here. This review verifies the cited version, not a claim that it is the newest version.

## Content verdict

Keep as **reference**. The actionable decision is to use a maintained OAuth implementation and review how its integration retains, correlates and protects per-attempt credentials. The crossed-pair exercise has observable success criteria: rejection without tokens or secret logs, success for fresh correct pairs, and independent service-side write denial. This is valuable when a team owns a protected connector, but not a prerequisite for engineers using an already configured coding assistant. The permissions/tool-design prerequisites are sensible; readers also need basic OAuth code-flow vocabulary, which the overview introduces.

All three animations isolate PKCE. Consent, redirect validation, issuer checks, TLS, client authentication where required, scopes, resource binding and operation authorization remain outside their visible mechanism. In the baseline's simplified continuation, a correct verifier redeems the intercepted code; applications must not infer that every provider leaves rejected codes reusable. The alternatives deliberately start fresh attempts after failure. Neither clearing records nor fading the screen means revocation. These limits are retained in metadata and the guide. No provider integration test was performed.
