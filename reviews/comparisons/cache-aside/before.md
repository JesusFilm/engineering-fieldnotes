## First comparative findings

1. **A, 00:00–00:06.5; 00:08.5–00:11.5:** The simplest visual topology. Caller -> application -> cache miss -> database read -> application cache fill -> caller is followed by a cache-only hit, with the unused database dimmed. The spinner makes the source path feel slower without fabricated latency numbers. Large actors and sparse traffic make ownership clearer than C's denser write/race sequence. However, anonymous envelopes, an unlabelled caller, and no on-screen topic title make this a weaker standalone learning object. The empty bar becomes full, but a newcomer must infer that it represents TTL rather than occupancy.
2. **A, 00:12.5–00:15; 00:16–00:23:** Clock plus draining bar and eviction lead to another miss/refill. This is a valid complementary mechanism, not a failure for omitting writers. It does not establish that an unexpired entry may already be stale, so it cannot alone support the guide's main caution. The cache remains full for several seconds before the visibly accelerated countdown: pedagogical time compression, not a literal lifetime trace. Final successful delivery has roughly a second of rest before fade; adequate but tighter than B/C.
3. **B, 00:00.5–00:06; 00:06.5–00:13.5:** Best introductory connection to the intended audience. The initial v1 hit establishes the normal case; source becomes v2, then the same cache path returns v1 to the agent. The value mismatch carries the lesson even without the HIT ≠ FRESH badge. Larger version fields and labels remain substantially more legible at 350px than C's policy rows and database footer. Pacing gives the stale outcome time to register.
4. **B, 00:14–00:23.5; 00:25–00:30:** DEL clears the cache; next lookup misses, reads v2 through the tool, fills cache, and delivers v2. A final warm hit verifies the recovered path. The recovery's origin is less explicit than C's editor path: the READ TOOL appears to initiate deletion without an incoming trigger. Treat that as a simplified recovery operation, not evidence that a hit detects freshness automatically. B omits the concurrent stale-fill race, so the healthy ending must not be sold as a consistency guarantee. Repeated successful hit costs a few seconds but usefully closes the causal loop.
5. **C, 00:00.5–00:06; 00:07–00:14:** Strongest advanced material. A refund policy goes from 30d to 14d, and only its cache row is deleted while tax remains. A miss fetches 14d; SET 14d visibly waits in the app while another editor write commits 7d and deletes again. The late SET then restores 14d. This is an actual counterexample to treating commit-then-delete as sufficient; neither A nor B shows it. But several very short write/delete transitions and tiny key/value text burden a first-time viewer. The hit checkmark at ~01.5s sits across the 30d value, obstructing the fact the viewer needs to compare. Source inspection should address that objective overlap.
6. **C, 00:15–00:23.5; 00:24–00:31.5:** Two successive hits deliver 14d while the database shows 7d. The continued draining lifetime bar demonstrates that hits do not renew this example's TTL. Expiry removes the row; a miss reloads 7d. Retain this race-focused alternative. Enlarging the policy values and separating hit feedback from row text would improve it materially without replacing its lesson. The second stale hit adds reinforcement but is the first place to shorten if pace needs tightening. The subtitle “INVALIDATE ON WRITE” understates the actual race lesson and could imply a recipe; “STALE FILL RACE” would orient viewers more accurately.
